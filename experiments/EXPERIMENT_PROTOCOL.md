# ROCm Performance Guard — Experiment Protocol V1

## Purpose

This document defines the controlled experiment methodology for evaluating
CPU GEMM optimization candidates generated by the Experiment Planner (`src/experiment.py`).

The protocol ensures:
- **Reproducibility**: Every experiment can be independently reproduced.
- **Fairness**: Baseline and candidate runs use identical conditions.
- **Safety**: No experiment mutates system state permanently.
- **Evidence-based decisions**: Accept/reject decisions are data-driven.

## Experiment Candidates

The Experiment Planner generates the following candidate categories:

### 1. Loop Tiling / Cache Blocking (HIGH priority, LOW risk)
- **Category**: Algorithm
- **Independent Variable**: `tile_size` ∈ {16, 32, 64, 128}
- **Hypothesis**: Partitioning the GEMM into cache-sized tiles reduces L2 misses
- **Expected Speedup**: 1.05x-1.3x
- **Acceptance**: Median latency decreases ≥5% with p95 not increasing >10%

### 2. Pre-Transposed B Matrix (MEDIUM priority, LOW risk)
- **Category**: Memory Access
- **Independent Variable**: `b_matrix_layout` ∈ {row_major_transposed, column_major_naive}
- **Hypothesis**: Contiguous inner-loop access improves cache line utilization
- **Expected Speedup**: 1.1x-2.0x
- **Acceptance**: Transposed layout achieves ≥5% lower median latency

### 3. Multi-Process Parallelism (HIGH priority, LOW risk)
- **Category**: Parallelism
- **Independent Variable**: `worker_count` ∈ {1, 2, 4, 8}
- **Hypothesis**: Row-chunk distribution across CPU cores reduces latency
- **Expected Speedup**: 1.5x-8x
- **Acceptance**: Median latency decreases ≥10% vs single-worker

### 4. Strassen Algorithm (LOW-MEDIUM priority, MEDIUM risk)
- **Category**: Algorithm
- **Independent Variable**: `strassen_crossover_threshold` ∈ {32, 64, 128, 256}
- **Hypothesis**: O(n^2.807) reduces total multiplications
- **Expected Speedup**: 0.8x-1.15x (marginal in pure Python)
- **Acceptance**: Median latency decreases ≥5%

### 5. Measurement Methodology Refinement (LOW-MEDIUM priority, LOW risk)
- **Category**: Measurement
- **Independent Variable**: `measurement_configuration` (warmup/iteration counts)
- **Hypothesis**: Additional iterations reduce CV%
- **Acceptance**: CV drops below 2% or reduces ≥30%

## Controlled Experiment Requirements

### Environmental Controls

Every experiment MUST satisfy:

1. **Identical Hardware**: Same CPU, same core count, same memory
2. **Identical OS State**: Same kernel, same services running
3. **Identical Python Environment**: Same Python version, same venv
4. **No Background Load**: Minimize competing processes
5. **Thermal Stability**: Allow CPU to reach stable temperature before timing
6. **Deterministic Input**: Same matrix dimensions, same deterministic matrix values

### Measurement Protocol

1. **Warmup**: Execute `warmup_runs` untimed iterations (default: 5)
2. **Measurement**: Execute `measurement_runs` timed iterations (default: 30)
3. **Timing**: Use `time.perf_counter_ns()` for nanosecond precision
4. **Statistics**: Report median, mean, p95, p99, stddev, CV%
5. **Comparison Metric**: Primary metric is `median_latency_ms`

### Single-Variable Design

Each experiment changes exactly ONE independent variable while holding
all control variables constant. This ensures any observed performance
change can be attributed to the manipulated variable.

## Execution Procedure

### Step 1: Verify Baseline Reproducibility

```
python -m src.benchmark --m 512 --n 512 --k 512 --warmup 5 --iterations 30
```

Confirm median latency is within ±2 stddev of the recorded baseline.

### Step 2: Generate Experiment Plan

```
python -m src.experiment
```

Review the generated plan. Select experiments to execute based on priority.

### Step 3: Execute Single Experiment

For each candidate:
1. Record pre-experiment environment state
2. Apply the single independent variable change
3. Run the benchmark with identical parameters
4. Record the result
5. Compare against baseline using the verification engine

### Step 4: Verify Results

```python
from src.verification import verify_optimization
result = verify_optimization(baseline, candidate, candidate_info="experiment-id")
```

### Step 5: Document Outcome

Record in the experiment results directory:
- Experiment ID
- Independent variable value tested
- Baseline result reference
- Candidate result
- Verification outcome (IMPROVED / REGRESSED / NO_MEANINGFUL_CHANGE)
- Observations and notes

---

## Acceptance / Rejection Criteria

| Outcome | Verification Status | Action |
|---|---|---|
| Clear improvement (≥5% latency reduction) | IMPROVED | Accept candidate, update baseline |
| Marginal improvement (<5%) | NO_MEANINGFUL_CHANGE | Record observation, do not adopt |
| Performance regression | REGRESSED | Reject candidate, investigate |
| Inconclusive (high variance) | NO_MEANINGFUL_CHANGE | Increase iterations, re-run |

---

## Safety Guarantees

- **No system modifications**: Experiments do not install packages, modify drivers, or change OS settings
- **No permanent state changes**: All experimental code changes are contained in source files
- **Reversible**: Every experiment has a documented rollback plan
- **No external dependencies**: All optimizations use pure Python standard library
- **No network calls**: All computation is local

## Limitations

1. Threshold-based acceptance does not establish statistical significance
2. Pure-Python performance is interpreter-bound; algorithmic gains may be masked
3. WSL2 scheduling overhead adds noise compared to bare-metal Linux
4. Results are specific to the tested hardware/software configuration
5. Experiment candidates are hypotheses — negative results are expected and informative
